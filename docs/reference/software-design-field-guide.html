How to use this guide

Read it once from top to bottom to learn the ideas. After that, use it as a lookup while you work.

If you are learning

Read parts 1 to 3 first. They hold the ideas everything else builds on: care about the design, know what complexity is, and build deep modules. One part per sitting is plenty.

If you are mid-project

Part 1

Mindset

Both books start with attitude before technique. The techniques only work if you care about the result and are willing to spend a little effort now to save a lot later.

Working code is not enough APoSD ch.3

Aim for a good design that also works, and pay for it with a steady 10 to 20 percent of your time.

Tactical programming means the goal is to get the current feature or fix working as fast as possible. Each shortcut seems reasonable. Because complexity builds up in small pieces, the shortcuts pile up, and the code gets slower and slower to work in.

Strategic programming treats working code as necessary but not as the goal. Most of the code you will ever write extends code that already exists, so the most valuable thing you can produce is a structure that is easy to extend.

What the investment looks like

  • Before: sketch a second design before committing to the first. Think about what is likely to change. Write the interface comment.
  • During: when you find a design problem, fix it properly. Do not patch around it.
  • After a change: the code should look as if it had been designed with that change in mind from the start. APoSD ch.16
  • Invest today. There is always another deadline, and postponed cleanups become permanent.
Do not overdo it

This is not big design up front. Nobody can picture a whole system well enough before building it. Make many small investments as you go.

The tactical tornado

Ousterhout's name for the developer who ships faster than anyone by leaving a mess behind. They look productive. The people who maintain their code afterwards pay the real cost.

Take ownership PP topics 1, 2, 53

Your work and your career are yours. When something goes wrong, bring options, not excuses.

  • You have agency. If your work or environment is not right, you can ask, learn, or move. Waiting and complaining changes nothing. PP Tip 3
  • Offer options. Before you say something cannot be done, work out what could rescue it: more time, a prototype, cutting scope, better tests. Say that. PP Tip 4
  • "I don't know" is fine when followed by "but I will find out".
  • Sign your work. Build things you would be happy to put your name on, and treat other people's code with the same respect. PP Tip 97

A quick test before delivering bad news: say it out loud first. If the explanation sounds weak to you, it will sound weak to them.

Good enough, on purpose PP topic 5, Tip 8

How good the software needs to be is a requirement to agree with its users, not something to decide alone.

"Good enough" does not mean sloppy. It means the level of polish is a choice with a cost, and the people who depend on the software get a say. A pacemaker needs far more care than an internal report. Many users would rather have something useful today than something perfect next year.

  • Ask how good it needs to be as well as what it needs to do.
  • Ship early and learn from real use.
  • Know when to stop. A painter who keeps adding layers loses the painting.
Does this conflict with strategic programming?

No. Good-enough is about scope and polish: which features, how refined. Strategic programming is about structure: whether the code stays easy to change. You can ship a small, rough-edged product on a clean design. That combination is usually the right one.

Watch for slow change PP topics 3, 4

Projects rarely fail in one moment. They drift, and drift is hard to see from inside.

Keep learning, and question what you learn PP topic 6

What you know loses value over time. Top it up on a schedule, and do not accept claims on hype or authority.

The book treats knowledge like an investment portfolio: add to it regularly, spread it across different areas, mix safe choices with a few risky ones, and review it now and then. PP Tip 9

Learning something you never use at work still pays, because it changes how you think. Knowing a second style of programming changes how you write in your first.

Questions for anything you read or are told PP Tip 10

  • Ask "why?" and keep asking of each answer until you reach the root.
  • Who benefits from me believing this?
  • In what context is this true? "Best practice" for whom?
  • What happens next, and what happens after that?

This applies to this guide as well. Both books are opinions backed by experience. Test the ideas against your own code.

Communicate deliberately PP topic 7

A good idea that does not reach the other person has no effect. Treat writing with the same care as code.

  • Know what you want to say before you start. Outline first.
  • Know your audience. The same change is "less to maintain" for a manager and "a new API to learn" for a developer.
  • Pick the moment and the form. If unsure how much detail someone wants, ask.
  • Listen, and always reply, even if only to say you will reply properly later.
  • Keep documentation next to the code so it is updated with it. PP Tip 13

Writing is "just another programming language": the same rules apply. Say each thing once, make it easy to change, and automate what you can. PP Tip 11

Part 2

Complexity, the real enemy

Software is not limited by physics. It is limited by how much of it people can hold in their heads. This part defines the problem so that the rest of the guide can aim at it.

What complexity is APoSD ch.2

Complexity is anything about the structure of a system that makes it hard to understand or hard to change.

This is a practical definition. Size is not the measure. A large system can be easy to work on and a small one can be a nightmare. Three points follow from it:

  • The reader decides. If your code seems simple to you but confuses other people, it is complex. Ask them where they got lost.
  • It is weighted by traffic. Complexity in a corner nobody visits costs little. Complexity in code people touch every day costs a lot. Hiding a hard thing behind a clean interface is nearly as good as removing it.
  • Fewer lines is not the goal. Sometimes the longer version is simpler because the reader has less to work out.
As a rough formula

Total complexity = for each part of the system, (how complex that part is) × (how much time developers spend in it), all added up.

Three symptoms, two causes APoSD ch.2

You feel complexity in three ways. It comes from two sources. Learn to name them and you can point at what is wrong.

One example, all three symptoms

A site shows a banner colour on every page.

Change amplification
# home.py
banner = "#0b6e75"
# about.py
banner = "#0b6e75"
# ...and 40 more pages
One obvious home
# theme.py
BANNER_COLOUR = "#0b6e75"

# every page
from theme import BANNER_COLOUR
Unknown unknown: a hidden dependency on the same decision
# checkout.py: a darker shade for emphasis, worked out by hand from the banner colour
EMPHASIS_COLOUR = "#084f54"
# Change BANNER_COLOUR and this page is silently wrong. Nothing tells you it exists.

The fix for the last case is to make the dependency visible: compute the shade from BANNER_COLOUR, or define both in theme.py side by side.

Questions to ask about any change

  • How many places did I have to edit?
  • How much did I have to know before I could do it safely?
  • Was there anything I could not have found out by reading the code?

Complexity arrives in small pieces APoSD ch.2 PP topic 3

No single shortcut makes a system unmanageable. Hundreds of small ones do, and each was easy to excuse at the time.

This is why "just this once" is dangerous. One extra special case, one vague name, one hidden dependency: none of them matters alone. Once they pile up, removing any one of them makes no visible difference, so nobody bothers.

The Pragmatic Programmer describes the same slide with the broken window. A building with one unrepaired broken window soon collects more, because the window signals that nobody cares. Code works the same way. A neglected hack tells the next person that hacks are acceptable here.

  • Fix small problems when you see them. If you cannot fix it now, mark it clearly so it reads as known damage and not as the standard. PP Tip 5
  • Treat "it is only a small thing" as a reason to care, not a reason to skip.
  • Keep clean code clean. People take far more care in a codebase that is visibly looked after.

The single test: is it easier to change? PP topic 8, Tip 14

Good design is easier to change than bad design. Nearly every design principle is a special case of this one.

The Pragmatic Programmer calls this ETC, for Easier To Change. Decoupling helps because separate parts can change separately. Good names help because you must read code before you can change it. Removing duplication helps because a fact stored once only needs changing once.

ETC is a value, not a rule. A value is something you steer by when no rule tells you what to do. When you cannot tell which of two options is better, ask which one leaves the code easier to change later.

  • Each time you save a file, ask: did that make the system easier or harder to change?
  • When you truly cannot tell, make the code replaceable. Keep the piece small, separate and behind a clear boundary, so that whatever happens it will not block you.
  • Write the situation down and note what you chose. When the code next needs changing, look back and see whether you guessed right. This is how the instinct gets trained.
How the two books line up

ETC and "reduce complexity" are the same goal seen from two sides. Ousterhout describes what makes code hard to work with. Thomas and Hunt describe what you want instead. Use whichever question is easier to answer in the moment.

Part 3

Designing modules

A module is any unit with an interface and an implementation: a function, a class, a package, a service. This part is about where to draw the boundaries and what to put behind them. It is the heart of A Philosophy of Software Design.

Make modules deep APoSD ch.4

The best modules give you a lot of behaviour through a small, simple interface.

Think of the interface as the cost of a module: it is what every user has to learn. The behaviour behind it is the benefit. A deep module has a low cost and a high benefit. A shallow module makes you learn almost as much as it saves you.

The interface is more than the signature. It has a formal part that the language checks (names, parameters, types) and an informal part that only comments can express: what the call does, side effects, and rules such as "call connect() before send()". If a caller needs to know it, it is part of the interface.

Shallow: costs more than it saves
class Settings:
    def __init__(self):
        self._values = {}

    def set_null_for(self, key):
        # One line. The caller could have
        # written this just as easily.
        self._values[key] = None
Deep: one call hides real work
def load_settings(path):
    """Return the app settings as a dict.

    Reads the file, applies defaults,
    checks types, and expands "~" in
    paths. Raises SettingsError with a
    readable message if the file is bad.
    """
    ...
  • For each module ask: how much must a caller know, compared with how much this does for them?
  • Make the common case need no thought. Give sensible defaults so most callers never see the rare options.
  • Do not create a class or function just because small feels tidy.
Red flag: Shallow Module

The interface is barely simpler than the implementation. Lots of tiny classes and one-line methods are the usual sign. Ousterhout calls the habit of making many small classes classitis: each class looks simple, but the system as a whole has far more interfaces to learn.

Hide design decisions APoSD ch.5 PP topic 28

Each design decision (a file format, a data structure, a rule) should be known in exactly one module.

This is how modules become deep. When a module fully owns a decision, the decision can change without anyone else noticing, and the interface gets simpler because there is less to explain. The opposite is information leakage: the same knowledge appears in two or more places, so they must change together.

Leakage has two forms. The visible form goes through the interface, such as a method that returns the internal dictionary. The hidden form is worse: two modules both quietly know the same thing, and nothing in the code links them.

Leak: two modules know the format
def read_scores(path):
    lines = open(path).read().split("\n")
    # knows: one "name,score" per line
    return [l.split(",") for l in lines]

def write_scores(path, rows):
    # knows the same thing, separately
    text = "\n".join(
        f"{n},{s}" for n, s in rows)
    open(path, "w").write(text)
Hidden: one owner of the format
class ScoreFile:
    """Scores stored on disk.

    The file layout is private to this
    class. Callers only see (name, score)
    pairs.
    """
    def __init__(self, path): ...
    def load(self): ...
    def save(self, scores): ...

The trap: splitting by order of events

The code on the left came from thinking "first we read, then we write", so it made one piece per step. This is temporal decomposition: structuring code by the order things happen. It feels natural, but the same knowledge is usually needed at several points in time, so it ends up duplicated. Split by what each piece needs to know, not by when it runs.

  • When you see the same knowledge in two places, ask: how can I reorganise so only one module knows this?
  • Do not return internal data structures. Offer get_parameter(name), not the whole dictionary.
  • Marking a field private is not hiding if getters and setters expose it anyway.
  • Do the right thing by default. If the module already has the information, it should not ask the caller for it.
Red flags: Information Leakage, Temporal Decomposition, Overexposure

Leakage: one decision shows up in several modules. Temporal decomposition: the structure mirrors execution order. Overexposure: to use a common feature, callers must learn about rare ones.

Do not overdo it

Only hide what callers do not need. If callers truly need a piece of information, such as whether a network message was lost, hiding it makes the module useless to them.

Make interfaces somewhat general APoSD ch.6

Build what you need today, but shape the interface so it is not tied to today's one use.

A general interface is usually smaller and simpler than a specialised one, even if you never reuse it. The reason is that specialised interfaces carry knowledge from their caller, which is a leak.

Ousterhout's example is a text editor. One team gave the text class a method per key: backspace(cursor), delete(cursor), delete_selection(selection). Every new user-interface feature needed a new method, and the text class had to know about cursors and selections. The general version needs only two methods:

A general text interface
text.insert(position, new_text)
text.delete(start, end)

# The UI layer expresses each key in terms of those two:
# Backspace key:
text.delete(cursor - 1, cursor)
# Delete key:
text.delete(cursor, cursor + 1)

The UI code is a line longer and far more obvious. The text class knows nothing about keys, and the same class would work for a find-and-replace tool.

Three questions to find the right level

  1. What is the simplest interface that covers everything I need right now?
  2. In how many situations will this method be used? If the answer is one, it is probably too specialised.
  3. Is this easy to use for what I need today? If not, I have gone too general.

Also remove special cases. Design the normal case so the edge case needs no extra code. In the editor, "no selection" was a flag checked everywhere. Treating it as an empty selection, where start equals end, made every check disappear.

Compare with The Pragmatic Programmer

PP warns against guessing the future (Tip 43 Avoid Fortune-Telling). The two fit together: do not add features you might need, but do choose a shape for the interface that does not lock in today's caller.

Each layer should add something APoSD ch.7

If two neighbouring layers look alike, one of them is probably not earning its place.

As a call travels down through a system, the way of thinking about the problem should change at each step. A file is "a stream of bytes" at one level, "numbered blocks" below that, and "commands to a device" below that. When a layer only repeats the layer under it, it adds an interface to learn and nothing else.

Pass-through methods
class Document:
    def __init__(self):
        self._text_area = TextArea()

    # Each method only forwards. Document adds an interface but no behaviour.
    def insert(self, position, text):
        return self._text_area.insert(position, text)

    def cursor_offset(self):
        return self._text_area.cursor_offset()

Fixes, in the order to try them: let callers use the lower class directly, move behaviour so each class has a clear job, or merge the two classes.

Same signature is fine when real work happens. A dispatcher that picks which function to call is doing a job. Several classes implementing one shared interface are also fine.

Pass-through variables

A related problem is a value handed down through five functions that do not use it, only so the sixth can. Ousterhout's usual fix is a context object: one object that holds system-wide settings and shared services, stored by the major objects when they are created. Keep its contents read-only where you can, because it shares most of the dangers of global data.

Red flag: Pass-Through Method

A method does nothing but hand its arguments to another method with a similar signature. The division of responsibility between the two classes is unclear.

Decorators and wrappers

A wrapper class that adds one small feature to another class is usually shallow. Before writing one, ask whether the feature could live in the class itself, or stand alone.

Pull complexity downward APoSD ch.8

When something hard has to be dealt with, the module should deal with it so its callers do not have to.

A module is written once and called from many places. Difficulty handled once on the inside is cheaper than difficulty handled at every call site. So a simple interface matters more than a simple implementation.

The tempting shortcuts go the other way. Not sure what to do with a problem? Raise an exception and let the caller decide. Not sure what value is right? Add a setting. Both feel responsible, and both push your problem onto every user of your code.

Pushes the decision up
def fetch(url, retry_delay_ms):
    # Every caller must guess a delay.
    # Most will guess badly.
    ...
Handles it inside
def fetch(url):
    # Measures how long recent requests
    # took and waits a multiple of that
    # before retrying. Adapts by itself.
    ...
  • Before adding a setting, ask: will the user really know a better value than this code can work out?
  • If you must expose a setting, give it a good default.
  • Before raising an error upward, ask whether the caller is any better placed to handle it.
Do not overdo it

Pull complexity down only when it belongs with what the module already does, it makes callers simpler, and it makes the interface simpler. A backspace() method on a text class fails this test: it drags user-interface knowledge into a module that should not have it.

Together or apart? APoSD ch.9

Split code when the pieces are truly independent. Keep it together when you would have to read both pieces to understand either.

Splitting is not free. Every split adds an interface, adds code to connect the pieces, and moves related things further apart. So size alone is a poor reason to split.

How long should a function be?

Long enough to do one thing completely. A long function with a simple signature that reads top to bottom is fine. Split a function in only two cases: a self-contained subtask can be pulled out so that each part reads without the other, or the function does two unrelated jobs that callers want separately.

Red flags: Conjoined Methods, Special-General Mixture, Repetition

Conjoined methods: you keep flipping between two functions to follow one idea. Merge them. Special-general mixture: a general mechanism contains code for one specific use. Move the specific code up to its user. Repetition: the same non-trivial code keeps appearing, so an abstraction is missing.

A real disagreement

Some well-known advice says functions should be only a few lines long. Ousterhout disagrees: once a function fits comfortably on a screen, making it shorter helps little, while each extra function adds an interface. Depth first, then length.

Decide what matters APoSD ch.21

Design is choosing the few things that matter, making them prominent, and hiding the rest.

Much of this part is one idea applied repeatedly. An interface shows what matters to callers. A name is the few words that say the most. A default hides what rarely matters.

  • Look for leverage: one mechanism that solves many problems, or one fact that explains many behaviours.
  • Shrink the list. Fewer required parameters, fewer settings, fewer places where each important thing is visible.
  • Check that the most visible parts of your interface are the most important ones.

The two ways to get this wrong are opposites. Treat too much as important and you get clutter and shallow interfaces. Miss something important and callers must rebuild it themselves or trip over it.

Part 4

Keeping code easy to change

Part 3 was about what goes inside a module. This part is about the connections between modules. It is the heart of The Pragmatic Programmer: fewer connections, and each fact stored once.

DRY: say each thing once PP topic 9, Tip 15

Every piece of knowledge should have one clear, authoritative home in the system.

DRY stands for Don't Repeat Yourself. It is the most misread principle in programming. It is not "never have two pieces of code that look alike". It is about knowledge: a rule, a format, a decision. If the same knowledge is written down in two places, one day you will change one and forget the other.

The test: when one fact changes, do you have to edit more than one place? If yes, that fact is duplicated, even if the two places look nothing alike (code and a comment, a database schema and a class, a constant and a document).

Duplicated knowledge
class Line:
    def __init__(self, start, end):
        self.start = start
        self.end = end
        # Length follows from start
        # and end, yet is stored too.
        # Change end and it is wrong.
        self.length = distance(start, end)
One source of truth
class Line:
    def __init__(self, start, end):
        self.start = start
        self.end = end

    @property
    def length(self):
        # Always worked out from the points.
        return distance(self.start, self.end)

Same code is not always the same knowledge

Leave these two apart
def validate_age(value):
    return isinstance(value, int) and value > 0

def validate_quantity(value):
    return isinstance(value, int) and value > 0

# The bodies match today by coincidence. They express two different rules.
# A minimum age of 18 would change one and not the other.

Merging them would tie together two things that only happen to agree right now. That creates a dependency where none existed.

Where duplication hides

The same idea in APoSD

Ousterhout's information leakage is DRY seen from the design side: one decision known in several modules. His Repetition red flag is the code-level version. Both books also agree on documentation: write each explanation once and point to it from elsewhere.

Orthogonality: keep unrelated things unrelated PP topic 10, Tip 17

Two parts are orthogonal when you can change one without touching the other.

The word comes from geometry: two lines at right angles are independent. The book's picture of the opposite is a helicopter, where every control affects every other, so the pilot must constantly correct. A codebase where each change breaks three other things feels the same.

The test: if the requirements behind one feature changed dramatically, how many modules would need editing? The ideal answer is one. Moving a button should never need a database change.

What you gain

  • Changes stay local, so they are quicker to make and to test.
  • A fault in one part is contained and that part can be replaced.
  • You are less locked in to one vendor or library, because it only touches a small area.
  • Write "shy" code: it shows nothing it does not need to, and relies on nothing it does not need.
  • Use your tests as a meter. If a unit test must set up half the system first, the unit is not independent.
  • Count how many files each bug fix touched. Scattered fixes mean coupled code.
  • Do not use real-world identifiers you do not control (phone numbers, email addresses) as keys. They change.
DRY and orthogonality work as a pair

DRY removes duplicated knowledge within the system. Orthogonality removes dependencies between its parts. In Ousterhout's terms, both reduce change amplification.

Do not reach through objects PP topic 28, Tips 44 to 46

Ask an object to do the job. Do not pull out its insides and do the job yourself.

The warning sign is a "train wreck": a long chain of dots reaching through several objects. Each dot is something that code now depends on never changing.

Reaches through four objects
def apply_discount(customer, order_id, pct):
    totals = customer.orders.find(order_id).totals
    totals.grand_total -= totals.grand_total * pct
    totals.discount = pct
    # A new rule (no discount above
    # 40%) has no safe home: anyone
    # can edit these fields.
Tells the owner to do it
def apply_discount(customer, order_id, pct):
    order = customer.find_order(order_id)
    order.apply_discount(pct)
    # The order owns its totals and
    # its rules. The 40% limit goes
    # inside apply_discount, once.
  • Tell, don't ask. Do not make decisions based on another object's internal state and then update it. Tip 45
  • One dot as a rule of thumb. Be suspicious of a.b.c.d in your own application code. Splitting the chain across temporary variables does not fix it. Tip 46
  • Exception: chains through things that will not change are fine, such as the language's own library (names.sort()[0].upper()), and pipelines of data transformations (see below).
This is information hiding again

The left-hand version leaks the structure of customer, orders and totals into every caller. See Hide design decisions.

Avoid global data PP topic 28, Tips 47, 48

Global data is an invisible extra parameter to every function in the program.

Any code can read or change it, so you can never be sure what a function depends on, and you cannot test or reuse the function alone. A singleton with public fields is the same thing with a longer name. So is any shared changeable resource: a database, a file, the current directory.

  • Pass what a function needs as parameters.
  • If something truly must be shared everywhere, wrap it in an API you control so its form can change later. Tip 48

Think in transformations PP topic 30, Tips 49, 50

Every program turns input into output. Design it as a chain of small steps that each change the data a little.

Start from the requirement, name the input and the output, then find the steps between. Each step is a function that takes data in one form and returns it in the next. Data flows through like a river. It does not sit in pools inside objects that poke at each other.

Five largest files, as a pipeline
def five_largest_files(folder):
    """Return the five files under folder with the most lines."""
    paths = find_files(folder)                 # folder name    -> list of paths
    counted = count_lines(paths)               # list of paths  -> list of (path, lines)
    ordered = sort_by_lines(counted)           # unsorted       -> sorted, largest first
    return ordered[:5]                         # all            -> top five

Each function can be tested alone and reused anywhere its input fits. There is no hidden state to set up.

Errors in a pipeline

Do not pass raw values that might be missing. Have each step return a result that says whether it worked, and stop at the first failure. In Python the simplest form is to raise an exception from the failing step and catch it once around the whole pipeline. That is the same shape as one handler high up in part 5.

Part 5

Errors and defensive code

The two books seem to disagree here. One says check everything and crash early. The other says too much error handling is itself a major source of bugs. They are describing two different kinds of problem, and the first idea below shows how to tell them apart.

Which kind of problem is this? PP APoSD

Design away the errors you can, handle expected failures in as few places as possible, and crash loudly on anything that should be impossible.

Define errors out of existence APoSD ch.10

The best way to handle an error is to design the operation so the error cannot happen.

Error handling code is hard to write, rarely runs, and is rarely tested. Every exception a function can raise is also part of its interface, so a function with many exceptions is a shallow one. The first question is whether the "error" needs to exist.

An error by definition
def remove_tag(tags, name):
    """Remove name. Raises KeyError
    if name is not present."""
    if name not in tags:
        raise KeyError(name)
    tags.remove(name)

# Every caller now writes try/except
# or checks first.
Defined away
def remove_tag(tags, name):
    """Make sure name is not in tags."""
    tags.discard(name)

# If it was already absent, the job
# is already done. Nothing to handle.

The change is in the wording of the promise: from "delete this" to "make sure this is gone". Python slices already work this way. text[5:500] on a short string returns what exists and raises nothing, which saves every caller from clamping the numbers first.

Do not overdo it

Only define away errors nobody needs to hear about. If a caller needs to know that a payment failed or a message was lost, swallowing it is a serious bug. Hide what is unimportant, expose what is important.

Raising an error is easy. Handling it is the hard part. So reduce the number of places that handle.

Crash early PP topic 24, Tip 38

When something impossible happens, stop. A dead program does far less damage than a confused one that keeps running.

Once an assumption has been broken, you no longer know what state the program is in. Carrying on risks writing bad data somewhere important. Stopping at the point of failure also gives you the clearest possible evidence of what went wrong.

  • Do not catch errors you cannot do anything useful about.
  • Read error messages. They are information, not noise. Tip 32
  • Give every match or if/elif chain a final branch that raises, so an unexpected value is noticed.
  • If there is tidying to do (close files, release locks), do it, and then stop.
An impossible value is caught at once

Design by contract PP topic 23, Tip 37

For every function, decide what it requires, what it promises, and what always stays true. Write that down.

A contract written down and checked
def withdraw(account, amount):
    """Take amount out of account and return the new balance.

    Requires: amount > 0, and amount is not more than the balance.
    Guarantees: the balance falls by exactly amount and is never negative.
    """
    assert amount > 0, "amount must be positive"
    assert amount <= account.balance, "caller must check funds first"

    account.balance -= amount

    assert account.balance >= 0, "balance went negative"
    return account.balance
  • Be strict about what you accept and promise as little as you can. A function that accepts anything and promises everything needs a huge amount of code.
  • Checking that a user typed a sensible value is not a precondition. Bad input from outside is normal and needs ordinary validation, at the edge of the system.
  • Find the few rules that must never be broken across the whole system, such as "never charge a card twice". Write them where everyone will see them.
Link to APoSD

Ousterhout asks for the same information in every interface comment: behaviour, each argument, the result, side effects, exceptions, and anything the caller must ensure first. He adds: keep preconditions few. Each one is something every caller has to remember.

Assert what "cannot happen" PP topic 25, Tip 39

Whenever you think "that could never happen", add a check that proves it.

  • Assertions are for bugs, not for expected errors. Never use one to validate user input or check that a file exists.
  • No side effects. The check must not change anything. Code that behaves differently when checks are switched off is a trap.
  • Leave them on. Testing does not find every bug, and production is a rougher place than your test machine. Switch off only a check that is measurably too slow.
Python note

Python removes assert statements when run with the -O flag. For a check that must never be skipped, write if not condition: raise ... yourself.

Finish what you start PP topic 26, Tips 40, 41

The code that opens a resource should be the code that closes it, and the two should sit close together.

This applies to files, connections, locks, transactions and temporary data. When one function opens something and a different function is trusted to close it, a later change will break the pairing.

Opened here, closed somewhere else
def read_customer(self):
    self.file = open(self.path)
    return parse(self.file.read())

def write_customer(self, data):
    self.file.write(format(data))
    self.file.close()
    # If a later change skips the
    # write, the file stays open.
One owner, closed automatically
def update_customer(path, change):
    # "with" closes the file when the
    # block ends, even after an error.
    with open(path, "r+") as file:
        customer = parse(file.read())
        change(customer)
        file.seek(0)
        file.write(format(customer))
        file.truncate()

  • Release several resources in the reverse of the order you took them.
  • Always take the same resources in the same order everywhere. This avoids two pieces of code each waiting for what the other holds.
  • Think about slow build-up too: log files, temporary files, old rows. Is anything clearing them?

Part 6

Names, comments and obvious code

Part 2 named obscurity as one of the two causes of complexity. This part is the cure. The aim is code where a reader's first quick guess about what something means turns out to be right.

Write for the reader APoSD ch.18

Code is obvious when someone can read it quickly and their first guess about what it does is correct.

"Obvious" is decided by the reader, never by the writer. If a reviewer says something is unclear, it is unclear. Do not argue. Find out what they were missing and put it in the code.

When code is not obvious, the reader lacks some piece of information. There are three ways to supply it, best first:

  1. Design it away. Change the code so the information is no longer needed, for example by removing a special case.
  2. Lean on what readers already know. Follow the conventions of the language and the project.
  3. State it. Use a precise name or a comment.
The reader has to guess
def lookup(term_id):
    ...
    return (4, False)

The meaning travels with the value

    current_term: int
    vote_granted: bool

    ...

Things that hide meaning

  • Anonymous tuples and pairs returned from functions. Use a small named type.
  • Code that runs at a distance, such as event handlers and callbacks. Say in the comment when and by what it is called.
  • Surprises. A constructor that starts background threads, a function called get_data that writes a file. If code does something a reader would not expect, say so right there.
  • Cramped layout. Use blank lines between the steps of a function, with a short comment opening each step.
Red flag: Nonobvious Code

You cannot tell what a piece of code does or means from a quick read.

The principle behind it

Software should be designed for ease of reading, not ease of writing. A shortcut that saves the writer two minutes costs every later reader.

Choose names with care APoSD ch.14 PP topic 44, Tip 74

A good name creates the right picture in the reader's mind, is precise, and always means the same thing.

Ousterhout once spent six months hunting a bug that came from one name. A file system used block for two things: a position on the disk and a position within a file. In one place the wrong kind was used, and data was overwritten. Names like disk_block and file_block would have prevented it. The lesson: "close enough" names are not good enough.

  • Name the role, not the mechanism. Ask "why does this exist?"
  • Booleans read as true-or-false statements: is_empty, has_children, cursor_visible.

Comment what the code cannot say APoSD ch.12, 13 PP topic 7

A comment earns its place by telling the reader something they could not get from the code next to it.

Code can state what happens. It cannot state why a choice was made, what a value means, what the units are, or what a caller is allowed to assume. That knowledge was in the designer's head. If it is not written down, the next person must rediscover it or guess.

Most importantly, a comment is what makes an abstraction usable. If people have to read a function's body to learn how to call it, the function is hiding nothing.

Write the comment first APoSD ch.15

Write the interface comment before the body. If it is hard to write, the design is wrong, and you have found out for free.

  1. Write the comment for the class: what it represents.
  2. Write the signature and comment for each main function, with empty bodies.
  3. Adjust until the set reads well together.
  4. Add the main fields with their comments.
  5. Fill in the bodies.

The comment works as an early warning. A short comment that tells callers everything they need means a clean interface. A long, awkward one means a complicated interface. A comment that has to explain the internals means a shallow function.

Comments written afterwards are worse for a simple reason: by then you are looking at the code, so you describe the code. The reasoning behind it has already faded.

Red flag: Hard to Describe

A function or variable needs a long comment to describe it completely. Go back and simplify the thing being described.

Keep comments true APoSD ch.16

A comment far from its code will not be updated. Keep each one close, and write each fact once.

  • Close to the code. Put each comment right above the lines it describes, in the smallest block that covers them.
  • The further away, the more general. A comment at the top of a file should speak in broad terms, which survive small changes.
  • In the code, not only in the commit message. If a future reader needs to know why something is the way it is, they will look in the file.
  • Once. Document each decision in one obvious place and point to it from the others. A broken pointer is easy to notice. A stale copy is not.
  • Do not re-explain other code. A caller should not describe what the called function does. Link to outside documentation; do not retell it.
  • Read your own diff before committing and check every comment near a change.

Be consistent APoSD ch.17 PP topic 44

Do similar things in similar ways. Then learning one part of the system teaches you the rest.

Consistency lets readers make safe assumptions. When something looks like a pattern they know, it behaves like that pattern. This covers names, layout, how errors are reported, how modules are structured, and rules that are always true.

  • When in Rome. Before writing in a file, read around it and follow what is there.
  • Write conventions down where newcomers will find them.
  • Enforce with tools where you can: formatters, linters, checks before commit. People forget; scripts do not.
  • Do not change a convention because you have a better idea. A consistent codebase is worth more than a slightly better style in one file. Change it only with real new information, and then change it everywhere.
Do not overdo it

Consistency also means different things should look different. Forcing unlike things into one pattern misleads the reader.

Designing and planning

How to get from a vague request to a design you trust. The shared theme is feedback: you cannot think your way to the right answer in advance, so set things up to learn quickly and cheaply.

Small steps, fast feedback PP topics 27, 48, Tips 42, 43

Never move faster than you can check. Your rate of feedback is your speed limit.

The book's picture is driving at night. Your headlights light a fixed distance. Drive faster than you can stop within that distance and you will hit something. In software, the further ahead you plan, the less you can actually see.

  • Deal with the tightest constraint first and fit the rest around it.
  • Explain the problem aloud to someone, or to an object on your desk. Saying each step forces out the assumption you were skipping.
  • Step away. Answers often arrive while you are doing something else.

For agents

This is the rule most easily broken by generated code. Do not add calls, retries or parameters "until it works". State what each line is for, verify behaviour against documentation or a test, and say so plainly when something is unverified.

Refactor early and often PP topic 40, Tip 65 APoSD ch.16

Improve the structure of code in small, tested steps, as part of everyday work.

Refactoring means changing the internal structure of code without changing what it does. Software is more like a garden than a building. You plant, see what grows, move things, prune and weed, all the time.

When to do it

  • You find duplicated knowledge.
  • Two things that should be independent turn out to be tangled.
  • You understand the problem better than when you wrote the code.
  • You just got a test passing. Tidy now, while it is fresh.

How to do it safely

  1. Do not refactor and add features in the same step.
  2. Have good tests first. Run them constantly.
  3. Take short steps: rename one thing, move one function, then test.

If you need "a week to refactor", that is a rewrite, and a sign the small steps were skipped for too long. The cost only grows as more code comes to depend on the part that needs fixing.

Ousterhout's standard for any change

Do not ask "what is the smallest change that works?" Ask "what would this code look like if it had been designed with this change in mind?" and move toward that. If you are not making the design better, you are probably making it worse.

Tests are design feedback PP topics 41, 51, Tips 66 to 70, 90 to 94 APoSD ch.19

The biggest benefit of a test comes from writing it. A test is the first user of your code, and it shows you what the code is like to use.

If something is hard to test, it is usually tangled up with other things. Making it testable makes it better designed. Thinking about a test before writing the code often improves the code before it exists.

Thinking about the test changed the design
# First idea: reads the real database and has the rule built in.
def avid_viewers(): ...

# After asking "how would I test this?":
def avid_viewers(video_database, minimum_per_week=10):
    """Return people who watch more than minimum_per_week videos.

    The database is passed in so a test can supply its own, and the
    threshold is a parameter because the requirement may change.
    """

Rules both books agree on

  • Tests make change safe. Without them people are afraid to improve the design, so it decays.
  • Write a failing test before fixing a bug. If you fix first, you cannot be sure the test would have caught it. Tip 31
  • Find each bug once. Every bug a person finds gets a test, so no person finds it again. Tip 94
  • Test later means test never. Test as you go.
  • All tests pass, all the time. A test that is allowed to fail teaches everyone to ignore failures.
  • Treat test code like real code: clear, independent, maintained.

Coverage is not the goal

Every line runs, and the bug is still there
def share(a, b):
    """a and b are whole numbers from 0 to 999."""
    return a / (a + b)

# One test runs every line. There are a million possible inputs,
# and exactly one of them (0, 0) divides by zero.

What matters is the range of states the program can be in, not the lines executed. Tip 93 To check that your tests are worth anything, break the code on purpose and confirm a test fails. Tip 92

Property-based testing Tip 71

If you write both the code and its tests, the same wrong assumption can be in both. A property-based test states a rule that must always hold and lets a tool generate hundreds of inputs to try to break it.

Python, with the Hypothesis library
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_sorting_keeps_every_item(numbers):
    # Hypothesis calls this many times with different lists.
    assert len(sorted(numbers)) == len(numbers)

@given(st.lists(st.integers()))
def test_sorted_is_in_order(numbers):
    result = sorted(numbers)
    for earlier, later in zip(result, result[1:]):
        assert earlier <= later

When one fails, copy the failing input into an ordinary test so it is checked every time from then on.

On test-driven development

The books differ on writing tests first as a strict method. See Where the books differ. Both warn about the same failure: taking tiny steps toward passing tests while never deciding where the design is going.

Know how your code grows PP topic 39, Tips 63, 64

For every loop, ask how big the input can get and how the cost grows with it.

Big-O notation describes how time or memory grows as the input size n grows. It gives the shape of the curve, not actual seconds.

  • Check your estimate by timing real code on real data at a few sizes. Tip 64

Performance without the mess APoSD ch.20 PP topic 39

Simple code is usually fast code. Measure before you optimise, and undo any optimisation that did not help.

There are two ways to get this wrong. Optimise everything and you get complicated code that is no faster where it counts. Ignore performance and you get a system that is slow everywhere with no single thing to fix. The middle path is to know what is expensive and choose designs that are efficient without being complicated.

Things that are always expensive

  • Network calls, especially over the internet.
  • Reading and writing storage.
  • Allocating lots of small pieces of memory.
  • Jumping around memory instead of reading it in order.

The routine

  1. Measure first. Intuition about what is slow is unreliable, even for experts. Find the few places that really take the time.
  2. Look for a basic fix: a cache, a better algorithm, a better data structure, fewer network trips.
  3. If there is none, redesign the hot path. Ask what the least possible work is for the common case. Check for all the special cases once at the start, and send them down a separate, simple path.
  4. Measure again. If the change did not make a real difference, take it out, unless it also made the code simpler.

Clean design helps speed directly. Deep modules do more per call with fewer layers to cross, and special cases that were designed away need no code to check for them.

Debugging PP topic 20, Tips 29 to 34

Debugging is problem solving. Reproduce the bug, read what the system tells you, narrow it down by halves, and question what you "know".

  • Fix the problem, not the blame. It does not matter whose fault it is. Tip 29
  • "That's impossible" is always wrong. It happened. Tip 30
  • Suspect your own code first. The bug is almost never in the language, the operating system or a major library. Tip 33
  • "I only changed one thing." Then that thing is the cause, however unlikely it seems.
  • Do not assume, prove. A surprising bug means something you trusted is false. Do not skip code because you "know" it works. Tip 34
  • Explain it aloud to a person or an object on your desk, step by step.
  • Keep notes as you go, so you can return to where you were after a dead end.
  • For problems over time, such as events and concurrency, add trace output in a consistent format a script can read.

After a surprising bug

  • Add or fix the test that should have caught it.
  • If bad data travelled a long way before failing, add an earlier check.
  • Look for the same mistake elsewhere and fix it now.
  • If it came from a wrong assumption, tell the team. Others may share it.

Events and concurrency

Real programs respond to things that happen at unpredictable times, and often do several things at once. Both are hard mainly for one reason: shared state. This part is drawn from The Pragmatic Programmer.

Shared state is incorrect state PP topic 34, Tips 57, 58

If two pieces of running code can both change the same data, neither can trust what it just read.

The book's example is a diner with one slice of pie left. Two waiters each look in the case, each see one slice, and each promise it to a customer.

Check, then act
if display_case.pie_count > 0:
    # Another waiter can take the
    # last slice right here.
    promise_pie(customer)
    display_case.take_pie()
One step, owned by the resource
class DisplayCase:
    def take_pie_if_available(self):
        """Return a slice, or None."""
        # The lock is released even
        # if an error happens inside.
        with self._lock:
            if self._pie_count == 0:
                return None
            self._pie_count -= 1
            return Slice()
  • List everything changeable that more than one task can reach. That includes files, database rows and the current folder, not only variables.
  • Replace "check, then act" with one call that the owner of the data performs as a single step.
  • Do not rely on every caller remembering to lock. Put the protection inside the resource.
  • Failures that come and go at random are usually concurrency bugs. Tip 58
  • Best of all, redesign so the state is not shared.

Remove ordering you do not need PP topic 33, Tip 56

Code often forces steps into a fixed order that the problem never asked for. Find the real dependencies.

"Call A before B" and "only one at a time" are couplings in time. Some are real. Many come only from the habit of writing steps one after another.

  • Write down the steps. For each, ask what truly has to be finished first.
  • Look for waiting that is not your code's work: network calls, storage, a person. Other work can go on during it.
  • Look for chunks that are independent of each other. They can run side by side and be combined at the end.
  • Then judge whether the gain is worth the extra care. What could overlap is not always worth overlapping.
Link to APoSD

A function that only works if another was called first is a hidden part of its interface. Ousterhout would ask you to remove the rule if you can, and document it clearly if you cannot.

Part 10

Tools, teams and projects

The habits around the code. Tool names date quickly, so this part keeps to the principles.

The three legs: version control, testing, automation PP topics 19, 51, Tips 28, 89 to 95

Every project needs everything in version control, tests that run automatically, and no manual steps.

Version control

  • Everything goes in: code, configuration, scripts, documents. Even solo, even for a one-week job. Tip 28
  • The one exception is secrets.
  • Builds, tests and releases are triggered by commits and tags, not by a person at a particular machine. Tip 89
  • A shared or synced folder is not version control.

Testing

  • Test early, often and automatically. Tip 90
  • Not done until the tests pass. Tip 91
  • Unit tests check a part alone. Integration tests check that parts keep their promises to each other, which is where many bugs live.
  • Test in conditions close to the real ones.

Automation

  • No manual procedures. A person following a list will eventually skip a step. Tip 95
  • Scripts do the same thing every time, and are themselves under version control.
  • One "small" manual step left in a build is a large broken window.

The spilled-drink test: if your computer were destroyed today, how long until a new one is in the same working state? If the answer is days, more of your setup belongs in version control.

Master a small set of tools PP topics 16 to 22, Tips 25 to 27, 35

Tools multiply ability. Learn a few general ones deeply, and add others only when a real need appears.

  • Keep knowledge in plain text. Text that a person can understand outlives the program that wrote it, and every tool can read, search, compare and version it. Use field names that explain themselves. Tip 25
  • Learn the command line. A graphical tool does only what its designers planned. The command line lets you combine tools and automate. If you describe a task as "click this, then that", it can probably be a script. Tip 26
  • Be fluent in your editor. The goal is no gap between thinking of a change and making it. When you catch yourself doing something repetitive, find the faster way and practise it. Tip 27
  • Have a scripting language for chores. Renaming, extracting, reformatting, generating. It turns a five-hour experiment into a thirty-minute one, which means you will actually try it. Tip 35
  • Keep a daybook. A running notebook of what you did, learned and decided. It is more reliable than memory, it holds ideas until you can use them, and writing things down makes you think.

Teams PP topics 47, 49, Tips 82 to 86

The same habits apply to a team as to a person: no broken windows, no duplicated work, small steps, shared ownership of quality.

  • Small and stable. The number of conversations needed grows much faster than the number of people. A team of 6 has 15 possible pairs. A team of 12 has 66. Tip 84
  • Able to deliver alone. One team should hold every skill needed to take a feature from idea to release. Hand-offs between specialist groups are where work waits. Tip 86
  • Quality belongs to everyone. It cannot be added afterwards by a separate group.
  • Put improvement on the schedule. Maintenance, learning and fixing the process only happen if time is set aside. "When we have a spare moment" means never. Tip 85
  • Work on code together. Two people at one problem bring different knowledge, and the one not typing is free to think about the bigger picture. Tip 82
  • Conway's Law. Systems end up shaped like the communication paths of the people who built them. Teams that do not talk build parts that do not fit. You can use this on purpose: organise people the way you want the software organised.

Do what works PP topics 48, 50, Tips 83, 87, 88

Being agile means responding to feedback. It is not a set of meetings and job titles.

Copying the visible habits of a successful company without what lies beneath them is a cargo cult. The practices suited that company's size, market and people. Yours differ.

  • Ask of every practice: why are we doing this, and does it work for us?
  • Try new ideas on a small scale. Keep what helps and drop the rest.
  • The real goal is to be able to deliver working software whenever users need it. Shorten the gap between releases step by step. Tip 88
  • A process that never changes is not agile.
Ousterhout's caution

Working in small increments can slide into tactical programming: one more feature, no time for design. His fix: let the unit of work be an abstraction, not a feature. Wait until a feature needs a new abstraction, then design that abstraction properly.

Responsibility to users PP postface, Tips 98, 99

Software affects people's safety, money and privacy. Two questions before you ship.

  • Have I protected the user? Have I thought through what happens when this fails or is misused, and stored only the data I need?
  • Would I be happy to be a user of this myself?

Where the books differ

The two books agree on far more than they dispute. These are the places where they pull apart, with a suggested way to hold both.

TopicThe Pragmatic ProgrammerA Philosophy of Software DesignA workable position
Writing tests first Useful, especially for beginners, because thinking about the test improves the design. Warns against following it blindly with no idea of the destination. Against it as a method. It focuses attention on getting features to pass and leaves no natural moment to design. One exception: write a failing test before fixing a bug. Always have tests, and always write the failing test first for a bug. For new work, sketch the design (or write the interface comments) before the first test, so the tests check a design and do not replace one.
How many comments Comment the "why". Do not comment every function mechanically, since that creates a second thing to keep up to date. Comment every class, every function and every field. It is cheaper than deciding case by case, and the interface comment is the abstraction. Every public class and function gets an interface comment that says something the signature does not. Inside functions, comment only intent and surprises. Both books reject comments that repeat the code.
Error handling Be paranoid. Check assumptions everywhere and crash early. Too much error handling causes bugs. Design errors away and handle the rest in few places. They address different cases. Use the decision flow: design away what you can, crash on broken assumptions, and handle outside failures once.
Configuration Put changeable values outside the code so behaviour can change without a rebuild. Every setting pushes a decision onto the user. Work the value out automatically where you can. Settings for facts about the environment. No settings for decisions the code could make. Defaults for everything.

Rules for agents

Compact operating rules for a coding agent working in a project that carries this guide. Each rule links to the section that explains it. Project instructions and the user's requests take priority over anything here.

Before changing code

  1. Read the surrounding code and follow its conventions for names, layout and error handling. #consistency
  2. Find the one module that should own the knowledge you are about to add. If it already exists somewhere, use it. Do not write a second copy. #dry #information-hiding
  3. For any new module or public function, sketch two different interfaces and choose the one that is simplest for callers. #design-twice
  4. Write the interface comment first. If it is hard to write, simplify the design. #comments-first
  5. If requirements are unclear, state the consequences of each reading and ask. Do not guess silently. #requirements

While writing code

  1. Prefer one deep function or class to several thin ones that forward to each other. #deep-modules #layers
  2. Do not return internal data structures or reach through other objects' internals. #tell-dont-ask
  3. Do not add a parameter, setting or exception to avoid making a decision. Decide, and give a default. #pull-down #configuration
  4. For each possible failure, use the decision flow: design it away, handle it once, or stop loudly. Never catch an error only to hide it. #error-decision
  5. Rely only on documented behaviour. Do not add calls or retries "until it works". If something is unverified, say so. #coincidence
  6. Use precise names. If a good name is hard to find, the thing may be doing two jobs. #naming
  7. Comments say what the code cannot: purpose, units, limits, reasons. Never restate the code. #comments
  8. Open and close each resource in the same place. #resources
  9. Avoid shared changeable state. If it must exist, give it one owner. #shared-state

  1. The change should look as if the code had been designed for it. Do not leave a patch on the side. #refactoring

Glossary

TermMeaning
AbstractionA simplified view of something that leaves out details you do not need.
AssertionA check in code for something that should always be true. Failing it means there is a bug.
Change amplificationOne simple change needs edits in many places.
Cognitive loadHow much you must hold in your head to do a task.
CohesionHow well the contents of a module belong together around one purpose.
CouplingA dependency between two pieces of code, so that they tend to change together.
Deep moduleA module with a simple interface and a lot of behaviour behind it.
Design by contractStating what a function requires, what it guarantees and what stays true.
DRYDon't Repeat Yourself. Each piece of knowledge has one home.
ETCEasier To Change. The test for choosing between designs.
Information hidingKeeping a design decision inside one module so others do not depend on it.
Information leakageThe same design decision known in more than one module.
InterfaceEverything a user of a module must know to use it, including what only comments can say.
InvariantSomething that is always true, such as "this list is never empty".
OrthogonalIndependent. Changing one does not affect the other.
Precondition / postconditionWhat must be true before a call / what the function guarantees after it.
PrototypeA throw-away experiment built to answer one question.
RefactoringChanging the structure of code without changing what it does.
Shallow moduleA module whose interface is nearly as complicated as what it hides.
Strategic / tactical programmingInvesting in the design as you go / only getting the current task working.
Temporal couplingA dependency on order in time, such as "call A before B".
Temporal decompositionSplitting code by the order things happen, which tends to duplicate knowledge.
Tracer bulletA thin, real, end-to-end slice of a system, built first and kept.
Unknown unknownSomething you need to know to make a change safely, with nothing to tell you it exists.
